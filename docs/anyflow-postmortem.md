# anyflow-embed の作業でなぜ行き違いが起きたのか（振り返りと改善案）

> 作成: 2026-08-15 / 対象: anyflow-embed（2026-08-05 〜 08-15、コミット73件）
> 目的: 「カンプを渡しているのに違うものが出てくる」「同じ不具合が何度も出る」の原因を、
> 記録に残っている事実からだけ特定し、次から同じことが起きない手順に落とす。

---

## 0. まず結論（3行）

1. **カンプは「止まった絵」しか決めていないのに、このサイトの中身は8割が「動き」だった。**
   決まっていない部分をClaudeが勝手に埋め、それが「勝手にデザインしている」に見えた。
2. **取れなかった数値を推測で埋め、しかもそれを黙っていた。** だから見た目が近いのに毎回ズレた。
3. **症状だけ直して原因を見に行かなかった。** だから「真っ白」3回・「切り替わりの違和感」4回と繰り返した。

## 2. 原因は5つ。どれも「作業者の注意不足」では直らない

### 原因① 仕様が3つあって、優先順位が決まっていなかった

このプロジェクトには仕様の出どころが3つあった。

| 出どころ | 決めていること | 決めていないこと |
|---|---|---|
| **Figmaカンプ** | 止まった絵（文字・色・位置・余白） | 動き、間合い、順番、hover、画面幅を変えた時 |
| **絵コンテ** | 場面の並び | 実際の秒数、イージング、止める位置 |
| **口頭・チャット** | その場の要望 | 前に決めたこととの整合 |

サイトの体験の大半は**「動き」と「間合い」**で決まる。つまり**一番重要な部分を、どの資料も決めていなかった。**
Claudeは進めるために自分で埋めた。それが「渡した資料に沿っていない」に見えた。

→ **これは指示ミスでも実装ミスでもなく、「決まっていない領域を誰が決めるか」の取り決めが無かっただけ。**

### 原因② 取れなかった数値を推測で埋め、報告しなかった

- `get_metadata` が返す「テキスト枠の幅」から字間を逆算した（枠はデザイナーが手で広げただけ。文字送りとは無関係）
- SVG書き出しでは文字がパスになって書体情報が消えるのに、見た目が合っていたので確認しなかった

**推測したこと自体より、「推測しました」と言わなかったことの方が問題。**
言っていれば、その場で「そこは◯◯だよ」と5秒で解決していた。
（→ 2026-08-14 に [DESIGN-SYSTEM-RULES.md](../DESIGN-SYSTEM-RULES.md) として制定済み）

### 原因③ 「確認しました」の中身が目視だった

- 書体が Text か Display かは、**見た目では判別できない**（実測したら5%差があった）
- プレビュー枠は**スクロールした先のスクショが撮れない**（真っ白に写る）。
  つまり確認できない環境で「確認しました」と言っていた

→ `getComputedStyle` / `getBoundingClientRect` / `canvas.measureText` で**実測**に切り替えた時点で、
この種のズレは出なくなった。

### 原因④ 一部だけ照合していた

最初の照合では主要19箇所を見た。しかしPlatform図のラベル群が対象から漏れ、
**カンプに増えていた「認証基盤」が実装に無い**ことに気づけなかった。

「カンプにあって実装に無いもの」は、**実装側を見ている限り絶対に見つからない。**
カンプ側から全部数える手順が要る。

### 原因⑤ 4,669行の単一HTMLを、範囲指定で置換していた

`index.html` 1ファイルに全セクションのCSS・JS・HTMLが入っている。
「実績のCSSを差し替える」時に開始と終了のマーカーがセクションをまたぎ、**隣のセクションを巻き添えで消した。3回。**

そして原因A（真っ白3回）の3回目は、**このB（巻き添え削除）が真犯人**だった。
つまり**構造の問題が、別の症状として何度も顔を出していた。**

## 3. なぜ「同じ不具合が何度も」起きたのか

真っ白3回の中身を並べると、はっきりする。

| 回 | 直した内容 | 直した層 |
|---|---|---|
| 1回目 | 早送りが最終フレームへワープ → 4倍速に変更 | 症状 |
| 2回目 | 白へ戻す処理が生スクロールに直結 → 差分基準に変更 | 症状 |
| 3回目 | **背景CSSそのものを巻き添えで削除していた** | 原因 |

**1・2回目は「白くなる条件」をいじっただけで、なぜ白くなるのかを見ていない。**
切り替わりの違和感4回も同じで、4回目にやっと「暗幕の下で板が2枚動いている」という真因に届いた。

→ **同じ症状が2回出た時点で、対処をやめて原因調査に切り替えるべきだった。**

## 4. 改善案（次からこうする）

### ルール1: 着手前に「決まっていない表」を1枚出す 🔴最重要

実装を始める前に、必ずこれを出してから手を動かす。

| 項目 | カンプから取れた | 取れなかった → こう決めた |
|---|---|---|
| 見出しの書体・サイズ | SF Pro Text 200 / 50px | — |
| 見出しが出る速さ | — | **0.6秒・ブラー付き（推測。要確認）** |
| 画面幅を変えた時 | — | **右から120px固定（カンプ2枚から推定）** |

**「取れなかった → こう決めた」の行が、行き違いの発生源そのもの。**
ここだけ先に見てもらえば、手戻りの9割は着手前に潰せる。

### ルール2: 動きは言葉で合意しない。触れるものを出す

秒数・イージング・間合いは、文章で読んでも判断できない。

- 案が複数ある時 → mockページを並べてURLで渡す（既存ルール。これは機能していた）
- 数値の詰め → **調整パネルを先に付けて、本人が触って決める**

実際、調整パネルを入れてからは「Claudeが決めて外す」が減り、
ヒデさん自身が値を決めて `📋 設定をコピー` で渡す流れに変わった。
**この方式を最初から採るのが一番効く。**（→ [tune-panel](../tune-panel/) として共通化済み）

### ルール3: 「確認しました」は実測とセットでしか言わない

- 目視で判断しない（書体・字間・余白は目で見て分からない）
- スクショが撮れない場所は「撮れないので実測で確認した」と書く
- 報告は **箇所 / カンプ値 / 実装値 / 一致か** の表（→ DESIGN-SYSTEM-RULES 4章）

### ルール4: 同じ症状が2回出たら、対処をやめて原因を探す

2回目の修正は「たぶんこれだろう」で当てにいっている状態。
**3回目に行く前に、必ず一段掘る。** 掘り方は「その症状を作っている一番下の層は何か」を口に出して確かめる。

### ルール5: 範囲でまとめて置換しない

- 置換の開始・終了マーカーは**同じセクション内**で取る
- セクションをまたぐ範囲指定は使わない
- 消す前に、消える範囲の**末尾5行**を目で見る

### ルール6: 1ファイル4,000行を超えたら分割を提案する

anyflow-embed は単一HTMLという性質上こうなったが、
**次に同じ規模のものを作る時は、着手時に分割を提案する**（セクションごとのCSS/JS）。
巻き添え削除は「注意すれば防げる」類ではなく、構造が呼び込んでいた。
