### 6. Claude Code で作って、Framer に逆輸入する

#### 6-1. 基本方針

**作り込んだところは Framer で手組みしません。Claude Code 側で作り、コード部品（.tsx）として Framer に持ち込みます。**

| なぜそうするか |
|---|
| 見た目が **100% そのまま**保たれる（作り直しによる劣化・ズレが起きない） |
| 「同じ質感になるか」の検証作業が要らない。すでに完成しているものを運ぶだけ |
| 直したくなったら **Claude Code 側を直して、貼り直すだけ** |
| 触りたい値だけ Property Control に出せば、Framer のプロパティ欄からノーコードで編集できる |

**Framer 側でやること / Claude Code 側でやること**

| Framer でやる | Claude Code から持ち込む |
|---|---|
| ページ構成、セクションの配置、Sticky | 惑星（WebGL） |
| テキスト、見出し、余白、罫線 | 開発者体験のモック画面 |
| 出現アニメーション（Appear / Text Effect） | 軌道グラフィック（SVG＋ドットの動き） |
| 実績の暗転（Scroll Transform） | スクロールを止める仕組み |
| ロゴの帯（Ticker Effect） | — |
| 導入事例のカード | — |

#### 6-2. 逆輸入する部品の一覧

| 部品 | 種類 | 状態 | 元の場所 |
|---|---|---|---|
| **スクロールを止める** | Override + Component | ✅ **作成済み** `framer/AnyflowPlayback.tsx` | 新規 |
| **惑星** | Code Component | 要作成（Claude に依頼） | `index.html` 3900〜4090 行 ＋ `DESIGNS` 1841〜2025 行 |
| **開発者体験のモック** | Code Component | 要作成（Claude に依頼） | `index.html` 1477〜1600 行（DOM 68個 ＋ CSS 32ルール） |
| **軌道グラフィック** | Code Component | 要作成（Claude に依頼） | `index.html` 内の SVG ＋ ドットの座標計算 |

#### 6-3. 受け渡しの手順

```
1. Claude Code に「◯◯を Framer のコード部品にして」と依頼する
2. .tsx ファイルを受け取る（framer/ フォルダに置かれます）
3. Framer で  Assets → Code → New File  を作り、中身を丸ごと貼り付ける
4. Insert メニューに出てくるので、キャンバスに置く
   （Override の場合は、対象レイヤーの Code Overrides から選ぶ）

```

> 枠（サイズと位置）だけ用意して、コード部品が入る場所を空けておいてください。

#### 6-4. スクロールを止める部品 ✅ 作成済み

**ファイル**: `framer/AnyflowPlayback.tsx`

中身は2つです。

**① PlaybackController**（Insert から置く・見えない部品）

貼りつけたい Sticky フレームの **中の一番上** に置きます。高さ 1px・透明なので、レイアウトには影響しません。

| プロパティ | 意味 | 入れる値 |
|---|---|---|
| セクション | どのセクションか | vision / results / dev / cases |
| 章の秒数 | 各章の長さ。カンマ区切り | ビジョン `6.6` ／ 実績 `3.8` ／ **開発者体験 `6.0, 5.6`** ／ 導入事例 `5.4` |
| 開始の許容ズレ | 画面上端から何 px の範囲で再生を始めるか | `8` |
| 次章までの送り量 | 章と章の間、何 px スクロールしたら次を始めるか | `120` |

**② Override**（中身のコンポーネントに掛ける）

章に合わせてバリアントを切り替えます。

| Override 名 | 掛ける先 | 必要なバリアント名 |
|---|---|---|
| `withVisionChapters` | Our Vision の中身 | `再生` |
| `withResultsChapters` | 実績の中身 | `再生` |
| `withDevChapters` | 開発者体験の中身 | **`章1` / `章2`** |
| `withCasesChapters` | 導入事例の中身 | `再生` |
| `withHideWhilePlaying` | スクロール誘導の矢印など | （不要・再生中は隠れます） |

> ⚠️ **バリアント名は Framer 側と完全に一致させてください。** 違うと切り替わりません。
> 名前を変えたい場合は `.tsx` の最下部の配列を書き換えます。

**動く仕組み**（Agent 向けの説明）

1. 置いた部品が、自分の位置を毎フレーム測ります
2. 画面の上端に着いたら → スクロール操作（ホイール・指・キー）を無効化し、1章目を開始
3. 指定秒数たったら → 無効化を解除し、その時のスクロール位置を覚えます
4. そこから 120px スクロールされたら → 2章目を開始（章が残っている場合）
5. 上に大きく戻ると、最初から流し直せる状態にリセットします

**既知のリスク**

- `body { overflow: hidden }` ではなく**操作そのものを無効化**する方式にしています（位置が飛ばないため）
- Framer 自身の慣性スクロールと競合する可能性があります。**実機で必ず確認してください**
- スマホの「慣性で流れている最中にロックが掛かる」場合、少し滑ってから止まります。気になる場合は「開始の許容ズレ」を大きくしてください

#### 6-5. 惑星

**Spline も動画も使いません。いまの WebGL をそのままコード部品にします。**

理由は `## 7` の比較表のとおりですが、要点はこれだけです。

- すでに完成していて、**ファイルサイズが極小**（コードだけ）
- 解像度に依存しないので、どんな大きさでも粗くならない
- 透過がそのまま効く（動画の最大の弱点が無い）
- 色・回転速度・粒の細かさを**あとから Framer のプロパティ欄で触れる**ようにできる

**Property Control に出す値**（＝ Framer から触れるようにする）

| 値 | いまの既定値 |
|---|---|
| 1回転の秒数 | 32 |
| 多面ゆらぎ | 0.37 |
| 質感の粒の強さ | 0.5 |
| 回転方向 | 1（順） |
| 回転軸の傾き | 0° |
| ランダムのゆらぎ | 0 |
| デザイン | （`DESIGNS` の中から選択） |

> ⚠️ WebGL が使えない環境（古い端末・GPU 無効）向けに、画像へ切り替わるフォールバックが元実装に入っています。コード部品にもそのまま持ち込みます。

#### 6-6. 開発者体験のモック

**Framer で手組みしないでください。** コード部品として持ち込みます。

理由 ── モックはコードの色分け（`POST` が緑、`Bearer` がピンク、`200 OK` が緑…）を含みます。Framer で手組みすると、色を変えた文字を1つずつ並べる作業になり、**必ずズレます**。

**Property Control に出す値**

| 値 | 例 |
|---|---|
| 表示する画面 | api / cli / sdk |
| チャットの問い | 「Slackの通知をkintoneに連携したい」 |
| チャットの返答 | 「Slack と kintone をつなぐフローを作成します。…」 |
| API のパス | `/v1/flows/flw_8Xk2/run` |
| レスポンス | `{ "status": "succeeded", "records": 3 }` |

これで、文言の差し替えは Framer 上でノーコードでできます。

### 7. 【参考】動くグラフィックの作り方 3種の比較

> 惑星を WebGL のまま持ち込む判断の根拠です。今後ほかのグラフィックを作るときの参考にもなります。

#### 7-1. WebGL（コードでその場に描く）← いまの惑星

ブラウザに毎フレーム計算させて、その場で絵を描かせる方式。

| | 内容 |
|---|---|
| **メリット** | ファイルが極小（コードだけ・数 KB〜）／どんな解像度でも粗くならない／色・速度・質感を**あとから数値で変えられる**／マウスやスクロールに即座に反応できる／無限にループしても継ぎ目が出ない |
| **デメリット** | 作るのにコードが要る（デザインツールでは作れない）／見た目の調整が「数値を変えて確認」の繰り返しになる／端末の GPU 性能に左右される／古い端末向けのフォールバックが要る |
| **向いている** | 抽象的なグラフィック、グラデーション、粒子、ノイズ、**ずっと流し続けるもの** |

#### 7-2. 動画（作った映像を再生する）

完成した映像ファイルをそのまま流す方式。

| | 内容 |
|---|---|
| **メリット** | 見た目が確実（作った通りに出る）／端末を選ばない／実装が一番簡単／どれだけ複雑な映像でも表示の負荷は同じ |
| **デメリット** | **ファイルが重い**（数 MB〜）／解像度が固定なので大きく使うと粗い／**透過が苦手**（対応形式が限られ、環境で崩れる）／**あとから一切変えられない**（色ひとつ変えるのに書き出し直し）／スクロール連動が苦手（再生位置の制御が難しい）／ループの継ぎ目が出やすい／iOS では自動再生に条件がある（無音・インライン再生が必須） |
| **向いている** | 実写、作り込んだ複雑な映像、**もう変更しないもの** |

#### 7-3. Spline（3D ツールで作って埋め込む）

GUI で 3D シーンを作り、ブラウザで動かす方式。

| | 内容 |
|---|---|
| **メリット** | **デザイナーが GUI で作れる**（コード不要）／本物の 3D なので角度・光・材質をあとから変えられる／マウス追従やスクロール連動が標準で用意されている／透過できる |
| **デメリット** | 3D を動かす仕組みごと読み込むので**初回が重い**（数 MB 規模）／スマホで発熱・電池を消費する／低スペック機で処理落ちする／Spline のサービスに依存する（仕様変更・料金）／**既存の WebGL コードは持ち込めない**（作り直しになる） |
| **向いている** | 立体物、質感のある 3D、**触って反応させたいもの** |

#### 7-4. 今回の結論

| | WebGL | 動画 | Spline |
|---|---|---|---|
| 見た目が今と同じになるか | ◎ そのもの | ◎ 録画なので同じ | ✕ 作り直し |
| ファイルの重さ | ◎ 数 KB | △ 数 MB | ✕ 数 MB＋実行環境 |
| 透過 | ◎ | ✕ 苦手 | ◎ |
| あとから色や速度を変える | ◎ | ✕ 不可 | ◎ |
| スマホ | ○ | ◎ | ✕ 重い |
| 作る手間 | ◎ **もう出来ている** | ○ 録画するだけ | ✕ 一から |

**→ WebGL のまま逆輸入する。** 唯一の弱点だった「コードが要る」は、Claude Code が書くので問題になりません。
